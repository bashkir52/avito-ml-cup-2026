## 3. Метрика и формат ответа

Для ленты из `M` кандидатов сортируем по убыванию score. При одинаковом score **отрицательные метки идут раньше положительных** — пессимистическая обработка равенств.

```text
DCG = sum(target_at_position_i / log2(i + 1)), i = 1..M
IDCG = DCG при идеальной сортировке, все target=1 перед target=0
NDCG = DCG / IDCG
Если положительных нет: NDCG = 1
Итог = обычное среднее NDCG по feed_id, без весов по размеру ленты
```

В текущих проверенных train/val лентах положительные есть всегда, что соответствует описанному фильтру сборщика. Метки test недоступны.

**Неоднозначность источника:** формула и основная метрика в «Описании» относятся ко всей ленте, но объяснение знаменателя внезапно называет `IDCG@30` и `DCG@30`. В `calculate_metrics.py` отдельно реализованы три метрики: `ndcg` без отсечения, `ndcg_at_10`, `ndcg_at_30`. CatBoost выбирает модель по `NDCG@30`, Transformer — по Logloss. Это разные критерии. Рабочее прочтение задания — основная NDCG без отсечения; для дальнейшего сравнения сохранять все три варианта, а окончательное подтверждение cutoff получить из актуальных разъяснений организаторов. Не смешивать DCG по всей ленте с IDCG@30.

Скрипт `calculate_metrics.py` требует закрытые ответы с колонками `feed_id, item_id, target, leaderboard_split`, причём должны присутствовать обе части `public` и `private`. Публичный val имеет вложенный `target` и не имеет `leaderboard_split`; CLI нельзя напрямую запускать на исходных файлах val. Правила метрики и функцию расчёта можно использовать при подготовленной локальной валидации.

| Колонка сабмита | Тип | Требование |
| --- | --- | --- |
| `feed_id` | `int32` | Тестовая лента |
| `item_id` | `int32` | Кандидат этой ленты |
| `score` | `float32` | Конечная оценка, без null / NaN / ±inf |

Нужны ровно все **2 904 806** пар шаблона: без повторов, пропусков и дополнительных пар. Порядок строк свободный. Score не обязан быть вероятностью; сопоставимость score между разными лентами не требуется. Public/Private — примерно 30/70 **по времени лент**, с сохранением одинакового времени в одной части и целой ленты в одной части. Пересечения пользователей разрешены устройством разбиения. В соревновании показывают Public, итог определяет Private.

## 4. Структура и сбор данных

```text
competition/
  readme.md
  sample_submission.parquet
  train/                       # val/ и test/ устроены аналогично
    impressions/
      part-*.parquet            # одна строка = одна полная лента
      _SUCCESS                 # пустой служебный маркер
    item_embeddings/
      data.meta                # JSON: dtype, shape, order
      data.memmap              # int8, (N, 128), C-order
```

Все части одного split читаются вместе. Parquet сжат ZSTD. В описании страницы указаны размеры загрузок: архив — 19,2 GB, отдельный шаблон — 16,8 MB, бейзлайны — 37,2 KB. Это сведения страницы о загрузках, а не наши измерения распакованного каталога.

| Split | Период по заданию, включительно | Назначение | Метки / позиции |
| --- | --- | --- | --- |
| train | 06–19 сентября 2026 | Обучение на полном train | `target` и `pos` есть |
| val | 22–24 сентября 2026 | Подбор параметров, локальная оценка | `target` есть, `pos` нет |
| test | 26–29 сентября 2026 | Предсказания для лидерборда | `target` и `pos` отсутствуют |

Правила из страницы «Данные» и README:

1. Сохраняются кандидаты с исходным `rank <= 300`, причём rank начинается с 0. Это условие на позицию, а не требование ровно 300 кандидатов.
2. Оставляются ленты минимум с пятью кандидатами и хотя бы одним положительным.
3. Согласно README, ранее просмотренные пользователем товары исключаются. Это не равнозначно отсутствию любых пересечений с историей: история содержит разные типы событий.
4. Val и test состоят из показов, где кандидаты были равномерно случайно перемешаны **до показа пользователю**. Обратная связь собрана после этих показов.
5. При подготовке val/test кандидаты перемешаны ещё раз согласованно со всеми признаками и метками. Исходная позиция не публикуется. В train `pos` сохранён и может иметь пропуски после фильтрации.
6. Преобразования `f1..f5` обучены на train и применены к остальным частям. Отдельные энкодеры не нужны; README бейзлайнов называет эти признаки нормализованными интерполированными бинами.

**Временная особенность, выявленная аудитом:** min/max timestamp в московском времени не полностью совпадают с календарными границами таблицы. Train: `2026-09-06 00:00:48` — `2026-09-20 00:00:48`; val: `2026-09-22 00:00:48` — `2026-09-25 00:00:48`; test: `2026-09-26 00:00:48` — `2026-09-29 23:58:40`. Это измеренные границы, причина сдвига не установлена. Не обрезать предоставленные split по календарным датам автоматически.

## 5. Справочник полей

`M` — число кандидатов данной ленты; `H` — длина истории, `0 <= H <= 256`. Ниже `float32` соответствует типу Arrow `float` в отчёте.

| Поле | Тип | Размер | Смысл и ограничения |
| --- | --- | --- | --- |
| `feed_id` | int32 | скаляр | Уникальная лента; не пересекается между split |
| `timestamp` | int32 | скаляр | Unix-время записи, секунды |
| `user_id` | int32 | скаляр | Общий словарь пользователей для всех split |
| `item_id` | list<int32> | M | Общие ID товаров для кандидатов и истории всех split |
| `category_id` | list<int8> | M | Категории; общий словарь с историей |
| `f1`, `f2`, `f3`, `f4`, `f5` | list<float32> | M каждый | Пять готовых числовых признаков; предметный смысл не раскрыт |
| `pos` | list<int16> | M | Исходная позиция, только train |
| `target` | list<int8> | M | Бинарная метка, только train/val; не признак |
| `item_id__embedding_idx` | list<int32> | M | Индекс в таблице эмбеддингов **этого split**; −1 = отсутствует |
| `user_embedding` | list<int8> | 128 | Один вектор всей ленты |
| `history__item_id` | list<int32> | H | Товары событий пользователя |
| `history__category_id` | list<int8> | H | Категории товаров истории |
| `history__event_type` | list<int8> | H | Закодированный тип события |
| `history__event_source` | list<int8> | H | Закодированный источник события |
| `history__item_id__embedding_idx` | list<int32> | H | Индексы эмбеддингов истории в таблице этого split; −1 = отсутствует |

- Все поля длины M разворачивать **одновременно**, сохраняя соответствие кандидатов, признаков, target и предсказаний. `user_embedding` и `history__*` в этот explode не входят.
- Все поля истории синхронны и упорядочены **от новых событий к старым**. История бывает пустой. Времени отдельного события в опубликованной схеме нет; доступны порядок и типы событий.
- ID пользователей и товаров — разные пространства. `0` зарезервирован для отсутствующего ID.
- Согласно README, категории имеют коды 1..53, события 1..10, источники 1..30; 0 означает неизвестное/отсутствующее. Не все коды обязаны встречаться. Это не исходные номера событий Авито; расшифровку не выдумывать.
- Одинаковый `item_id` может иметь **разные embedding_idx** в разных split. Переносить индексы между таблицами нельзя.
- `−1` нельзя передавать в NumPy как обычный индекс: он вернёт последнюю строку. Сначала маска наличия и заполнение отсутствующих векторов.
- Перед dot/cosine/нормами преобразовывать int8 в float32. Полную таблицу конвертировать не нужно: использовать `memmap` и нужные строки. Нулевой вектор обрабатывать без деления на ноль.

Полный пример чтения организаторов сохранён в приложении Б.

## 7. Официальные бейзлайны — что подтверждено кодом

| Свойство | CatBoost | Transformer |
| --- | --- | --- |
| Модель | CatBoostRanker, YetiRank | TransformerEncoder, без позиционных embeddings кандидатов |
| Вход | f1..f5, категория, dot, cosine, missing-флаг — 9 признаков | Вектор пользователя; для кандидата f1..f5, item-вектор, категория, missing-флаг |
| Контекст | Группа = feed_id | Пользовательский токен + все кандидаты ленты |

## 8. Выводы из изученного, существенные для дальнейшей работы

Это наши выводы, а не дополнительные правила организаторов:

1. **Единица задачи — целая лента.** Метрика даёт каждой ленте один вес, тогда как обычный BCE в Transformer усредняется по кандидатам. Нельзя считать эти цели эквивалентными.
2. **Val важнее случайного разбиения train для выбора модели.** Его сбор соответствует test; train не описан как состоящий только из случайно перемешанных показов. Позиционный и временной сдвиги могут влиять на переносимость результатов.
3. **Pos отсутствует при применении модели.** Подать train-pos как обычный признак обученной модели без отдельного обоснованного механизма нельзя. Индекс элемента массива val/test не восстанавливает исходный rank.
4. **История — отдельный доступный источник информации, пока не используемый бейзлайнами.** У примерно 14–15% событий проверенных историй нет item-вектора; категории и коды событий при этом остаются доступны. Пустую историю и отсутствующий вектор надо учитывать явно.
5. **Большинство val/test пользователей не встречается по ID в train.** Совпадают 4 370 из 13 741 val-пользователей и 8 263 из 27 309 test-пользователей. Признаки, завязанные исключительно на известный ID, должны иметь корректное поведение для новых пользователей.
6. **Сдвиг распределений наблюдается уже в простых статистиках.** В val/test ленты в среднем длиннее, чем в проверенном срезе train. Доля положительных в срезе train выше, чем в val. Эти сравнения описательные и не доказывают конкретную причину.
7. **Нельзя оценивать качество только по Logloss или только по Public.** Нужна согласованная с соревнованием локальная NDCG; Public и Private разделены по времени, а запросов к лидерборду мало.
8. **Есть ограничения памяти до начала обучения.** Полный explode train и временные копии векторов/тензоров могут быть дороже самого обучения; объём данных нужно учитывать заранее.
9. **Временные агрегаты требуют контроля утечек.** Target не является признаком; сведения из будущего и чужих validation-меток нельзя незаметно включать в обучение/признаки. Подробные правила финального переобучения на val в переданных текстах не заданы.

Каждая лента определяется идентификатором feed_id. Для каждого объявления в ней необходимо предсказать числовую оценку score: чем выше оценка, тем выше объявление должно находиться в ленте.

Целевая метка target бинарная:
- 1 — зафиксировано хотя бы одно событие из набора целевых действий;
- 0 — таких событий не зафиксировано.
Все события из целевого набора имеют одинаковый вес. Ранжирование выполняется внутри каждой ленты; сопоставимость оценок между разными лентами не требуется.

Используйте sample_submission.parquet как шаблон: сохраните все пары (feed_id, item_id) и замените score предсказаниями модели.

Требования к решению:
- ровно одна оценка для каждой пары из тестовой выборки;
- без пропущенных, лишних и повторяющихся пар;
- без пустых значений, NaN и бесконечных оценок.
Порядок строк не влияет на результат. Объявления сортируются по убыванию score внутри каждой ленты. Оценка не обязана быть вероятностью или находиться в диапазоне от 0 до 1.
Основная метрика соревнования — NDCG. Она учитывает положение положительных: чем выше они расположены, тем больше их вклад.

Для каждой ленты сначала рассчитывается:
```text
DCG = Σ target_i / log2(i + 1),  i = 1, …, число кандидатов
NDCG = DCG / IDCG
```
Здесь i — позиция после сортировки по предсказанной оценке, начиная с 1. IDCG@30 — значение DCG@30 при идеальном порядке, когда все положительные примеры расположены выше отрицательных.

Итоговая метрика — среднее NDCGпо лентам. Все ленты имеют одинаковый вес независимо от числа кандидатов. Чем выше метрика, тем лучше решение.

Особенности эталонного расчёта:
- при одинаковых score отрицательные примеры располагаются перед положительными;
- если положительных примеров в ленте нет, NDCG принимается равным 1. Это правило расчёта; сборщик датасета отбирает ленты с положительными примерами.
Тестовая выборка разделена хронологически: примерно первые 30% лент относятся к Public, оставшиеся 70% — к Private.

Граница выбирается максимально близко к 30% по числу лент. Ленты с одинаковым временем записи остаются в одной части, поэтому точная пропорция может немного отличаться. Каждая лента целиком относится к Public или Private; разбиение не гарантирует непересечение пользователей между частями.

feed_id	int32	Скаляр	Уникальный идентификатор ленты. Не пересекается между train, val и test.
timestamp	int32	Скаляр	Unix-время записи ленты в секундах.
user_id	int32	Скаляр	Обезличенный идентификатор пользователя. Нумерация общая для всех частей датасета.
category_id	list<int8>	M	Код категории каждого кандидата. Словарь общий с history__category_id во всех частях датасета.
f1	list<float32>	M	Нормализованный вещественный признак № 1.
f2	list<float32>	M	Нормализованный вещественный признак № 2.
f3	list<float32>	M	Нормализованный вещественный признак № 3.
f4	list<float32>	M	Нормализованный вещественный признак № 4.
f5	list<float32>	M	Нормализованный вещественный признак № 5.
pos	list<int16>	M	Исходная позиция кандидата, нумерация с 0. Есть только в train; после фильтрации позиции могут содержать пропуски.
target	list<int8>	M	Целевая метка кандидата: 1 — зафиксировано целевое действие, 0 — не зафиксировано. Есть только в train и val; это метка для обучения и оценки, а не входной признак модели.
item_id__embedding_idx	list<int32>	M	Индекс строки эмбеддинга кандидата в таблице item_embeddings/data.memmap этой части датасета. -1 означает отсутствие эмбеддинга.
item_id	list<int32>	M	Обезличенный идентификатор товара. Нумерация общая для кандидатов и истории во всех частях датасета.
user_embedding	list<int8>	128	Эмбеддинг пользователя.
history__item_id	list<int32>	H	Обезличенные идентификаторы товаров из истории пользователя.
history__category_id	list<int8>	H	Коды категорий товаров из истории. Используется тот же словарь, что и в category_id.
history__event_type	list<int8>	H	Категориальный код типа события пользователя.
history__event_source	list<int8>	H	Категориальный код источника события пользователя.
history__item_id__embedding_idx	list<int32>	H	Индексы эмбеддингов товаров из истории в таблице item_embeddings/data.memmap этой части датасета. -1 означает отсутствие эмбеддинга.
Все массивы длины M описывают кандидатов в одинаковом порядке. Например, item_id[i], f1[i], category_id[i] и target[i] относятся к одному объявлению. При разворачивании ленты в строки эти массивы нужно разворачивать совместно.

target — метка для обучения и оценки, а не входной признак модели. Положительный пример означает наличие хотя бы одного события из целевого набора. В сборщике все события этого набора имеют вес 1; число совершённых действий не увеличивает метку.

Идентификаторы и категории
Идентификаторы пользователей и объявлений заменены целочисленными номерами. Нумерация объявлений общая для кандидатов и истории во всех выборках. Пользователи имеют отдельное пространство идентификаторов. Положительные значения обозначают известные объекты, 0 зарезервирован для отсутствующего ID.

feed_id уникален во всём датасете и не пересекается между train, val и test. Это не означает, что пользователи или объявления обязательно различаются между выборками.

Категории кандидатов и истории используют общий словарь. Типы и источники событий также закодированы согласованно между выборками. 0 обозначает неизвестное или отсутствующее значение. Коды событий не являются исходными номерами событий Авито.

Признаки f1–f5 уже нормализованы. Преобразования числовых признаков обучены только на train и применены к val и test без повторного обучения. Отдельные файлы энкодеров для чтения датасета не нужны.

История пользователя
Поля history__* содержат до 256 событий, упорядоченных от новых к старым. Все массивы истории одной ленты имеют одинаковую длину H; элементы с одинаковым индексом описывают одно событие.

История может быть пустой. Кандидаты и история имеют отдельные массивы: M и H не обязаны совпадать. Эмбеддинг пользователя относится ко всей ленте и всегда содержит 128 компонент.

Эмбеддинги объявлений
Каждая выборка имеет собственную таблицу эмбеддингов item_embeddings/data.memmap. Для одного объявления индексы в train, val и test могут различаться, хотя item_id остаётся общим.

Поля item_id__embedding_idx и history__item_id__embedding_idx указывают на строки таблицы соответствующей выборки. Индексы начинаются с 0. Значение -1 означает отсутствие эмбеддинга: его нельзя использовать как индекс NumPy, иначе будет прочитана последняя строка таблицы.

Перед вычислением скалярного произведения, нормы и других операций переводите int8 в float32, чтобы избежать переполнения.

Пример чтения
Пример читает одну ленту train и эмбеддинги её кандидатов. NumPy memmap позволяет обращаться к отдельным строкам матрицы без загрузки всей таблицы в оперативную память.

import json
from pathlib import Path

import numpy as np
import polars as pl

split = Path("competition/train")
feed = (
    pl.scan_parquet(str(split / "impressions/part-*.parquet"))
    .head(1)
    .collect()
    .row(0, named=True)
)

embedding_dir = split / "item_embeddings"
meta = json.loads((embedding_dir / "data.meta").read_text())
embeddings = np.memmap(
    embedding_dir / "data.memmap",
    dtype=meta["dtype"],
    mode="r",
    shape=tuple(meta["shape"]),
    order=meta["order"],
)

indices = np.asarray(feed["item_id__embedding_idx"], dtype=np.int64)
present = indices >= 0
candidate_vectors = np.zeros((len(indices), 128), dtype=np.float32)
candidate_vectors[present] = embeddings[indices[present]].astype(np.float32)
user_vector = np.asarray(feed["user_embedding"], dtype=np.float32)
